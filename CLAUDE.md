# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A **Claude Code plugin marketplace**, not an application. It ships one plugin (`cadence`) made entirely of Markdown — there is no source code, build, lint, or test step. "Building" here means editing skill/command/reference `.md` files and their JSON manifests. Validation is by reading the prose for consistency, not by running a tool.

## Layout

```
.claude-plugin/marketplace.json      marketplace manifest → lists the cadence plugin, source ./plugins/cadence
plugins/cadence/
  .claude-plugin/plugin.json         plugin manifest (name/version/author)
  commands/                          slash-command entrypoints (thin — they load a skill)
    plan.md                       /cadence:plan        → loads cadence-planner
    ship.md                /cadence:ship → loads cadence-executor
    report.md              /cadence:report → renders <runDir>/report.md per
                                       cadence-executor/references/cycle-report.md (read-only)
  skills/
    cadence-planner/SKILL.md           the planner behavior + references/cycle-plan-template.md
    cadence-executor/SKILL.md          the TOP ORCHESTRATOR behavior + references/{task-agent,execution-state,pr-template,cycle-report}.md
```

The executor's behavior is deliberately split in two: `SKILL.md` is the **top
orchestrator's** playbook (preflight, dispatch, change detection, re-arm), while
`references/task-agent.md` is the **per-task agent's** playbook (spec/implement
phases, Monitor pass, JUDGE BEFORE YOU ACT, NO SILENT FIXES, PR conventions, tracker
sync) — every spawned agent is told to read it first. This keeps the orchestrator's
per-wakeup context small. When editing executor behavior, put it in the right file
and keep the SKILL.md one-paragraph summary of the agent in sync.

Commands are deliberately thin: each one resolves its `$ARGUMENTS` (a task list, a Linear/Jira key, or a plan-doc path) and hands off to the matching skill. The behavior lives in the `SKILL.md` files; the `references/*.md` are the templates and schemas those skills read at runtime.

## The two-skill pipeline (the core architecture)

The plugin implements a **plan → execute** handoff for parallel development cycles. Understanding the contract between the two skills is the whole point:

1. **`cadence-planner`** ingests tasks, runs deep parallel codebase analysis to compute each task's *touch set* (creates / edits / reads / shared surfaces), builds a dependency graph (declared deps + producer→consumer + write-write conflicts), and topologically levels tasks into parallel **waves**. It is **plan-only** — it writes a cycle-plan doc to `docs/plans/proposed/<YYYYMMDD-HHMM>-<slug>-<task-id>.md` and stops. It never implements or dispatches.

2. **`cadence-executor`** consumes that plan doc and autonomously drives every task to a merged PR, then keeps monitoring open PRs on a `ScheduleWakeup` loop until a **human** merges.

The handoff is by **file + metadata header**, not by memory: the planner records `Slug` and `Task-id` in the plan's metadata block, and the executor reads them from content (the filename is timestamped and not authoritative).

## Executor invariants (the rules that must never be broken when editing cadence-executor)

These constraints define the executor and appear throughout its `SKILL.md`. When editing, preserve them exactly:

- **NOTHING EVER MERGES INTO A JOIN BRANCH.** A join is scaffolding for a 2+-blocker task: branch your work **off** it so you compile against your blockers' code, but the **PR targets the integration branch, never the join**. A join merges nowhere, so anything merged *into* it is stranded off integration — the source branch is auto-deleted on merge, the work vanishes from the cycle, the exit gate runs without it, and a rescue PR has to be invented to carry it across (observed in production: `pagana-catalog-apps#38/#39` → `#41`). A task PR based on a join is a **defect**: re-target to integration immediately, log `pr.retargeted`, surface it. A join is **per task, never shared**, gets no PR, is never reviewed, and is simply deleted once its blockers land — there is nothing to re-target, because the PR was against integration all along. Its diff temporarily includes unmerged blockers' files: that is **declared, not hidden** ("Files changed: 34 — 8 this task's, 26 from #35 (not yet merged)") and shrinks by itself as blockers land. **Never open plumbing PRs as routine** — a PR with no task behind it means the topology broke, and it must read as the incident it is (`cycle-repair`, surfaced in `attention` + the report).
- **The plan (integration) PR carries the cycle plan as diagrams.** It is where a human goes to understand the *shape* of the cycle, and a table of rows can't show dependencies. Its body opens with two Mermaid diagrams rendered from the plan doc — **waves + dependencies** (what runs in parallel, what waits) and **branch topology** (where each PR is based) — above the task→PR map table. Nodes carry **task id + what it does + PR number**, the same identity rule as everywhere else. Diagrams are **structure, not status**: drawn once, never re-rendered as PRs move (GitHub already renders live status beside each referenced PR); redrawn only if the plan itself changes.
- **Stacked branch topology, and it never gates on merges.** One **integration branch** `cadence/<slug>-integration` holds the plan docs as a *plan PR → `main`* (opened draft). A task's PR base is derived from its blockers and is never `main`: **0 blockers** → integration; **1 blocker** → that blocker's branch (stacked); **2+ blockers** → branch off its own **join branch** `cadence/<slug>-t<id>-join` (integration with every blocker's branch merged in) but **target integration with the PR**; the join is built by the task's own agent so the task starts while its blockers are still open, refreshed as they advance, and simply deleted once they've all landed. Each task PR lands in integration; the plan PR into `main` is merged last, by the human.
- **Flow audit every tick — "waiting for a merge" is a defect.** Each tick classifies why every unfinished task isn't advancing. Agent-in-flight, awaiting human review, awaiting a human decision, blocked by a failed dep, and waiting for a blocker's *branch* to appear are legitimate; being held because another PR hasn't **merged** is not — it must be converted the same tick (build/refresh a join, merge the base in, re-target). Three consecutive ticks on the same non-dispatchable reason lands in `run.json.stalls` and the turn summary.
- **Sweep generated docs off `main`.** The planner writes the cycle-plan/design docs into the **`main` working tree**, where they sit *uncommitted/untracked*. When the executor creates the integration branch (as a **worktree**), it **moves** this cycle's in-scope docs (plan doc + this run's `docs/plans/proposed/` and `docs/superpowers/specs/` files) into that worktree, commits them there, and asserts the `main` checkout is left clean of cycle files. Out-of-scope uncommitted changes (the user's unrelated WIP) are never touched. This is what stops cycle files from stranding on `main`.
- **Never push/commit to `main`; never merge the plan PR.** The plan PR → `main` is the human's gate, unconditionally — no policy or approval hands it over.
- **Pins are read from the PLAN ON DISK, and the SHA is recorded.** Pin from the file, never from a copy of it in context. Plan docs get corrected minutes before a run precisely because someone reviewed them, and the copy handed over earlier in the session is not the document the human approved. At pin time: `git rev-parse HEAD`, re-read the plan, write `topology.planSha` + `topology.planReadAt`, and quote the plan's §-number and its **exact live text** in the `policy.pinned` event. A run once pinned `"NO join branches"` quoting §7.3 from a **stale draft held in context**, while the live document — committed **~2 minutes before run open** — mandated per-task joins and said in terms that the older conclusion was superseded. The wrong pin was logged as deliberate and undone only because **three spec agents independently refused their briefs and cited the file**. Agents doing the orchestrator's reading for it is not a safety net.
- **Policy is pinned at run open — an upgrade never changes the rules under a live run.** Monitoring spans days and `/cadence:ship` re-enters by re-reading the skill files, so a mid-run plugin upgrade would otherwise silently adopt new behaviour: a run whose human was told "merges are human-only" could start merging. `run.json` therefore records `policyVersion` (version at run open) and an **explicit** `approvalMergePolicy` (never absent). On resume: **no `approvalMergePolicy` → the run predates the feature → treat as `"off"` (human-only)**, write it, log `policy.pinned`, say so once; **installed version ≠ `policyVersion` → note the skew once** and keep behaving as the run started. Only the user opts an in-flight run into new policy, explicitly. Pinned promises: **merge policy, draft/readiness semantics, `main` safety, and the BRANCH TOPOLOGY** (`run.json.topology` — how a PR base is derived from blockers, written at run open). Topology is pinned because an upgrade once re-based a live cycle: a run opened under "0 or 2+ blockers → integration" was resumed after an upgrade to a join model, adopted it silently against the plan doc *and* an explicit user instruction in state, and stranded four tasks' merged work off integration (three recovery PRs to unwind). **The plan doc wins over the skill's default** where they disagree — the human read and approved that document — recorded as `topology.source = "plan"` and surfaced in one line; a topology drift found on resume keeps the pinned value and logs an `incident` (`kind: "topology.skew"`). Everything mechanical (conflict detection, tick cost, report richness) applies immediately — it changes nothing the user was told. The run-open announcement states the merge policy in one explicit line so it is auditable later.
- **Approval-authorized auto-merge (task PRs only).** An approving review by a **human** on a task PR is that human's authorization for the task's own agent to merge it into its base. It merges only when every guard holds in the same monitor tick: human (not bot) approval; approval not dismissed or superseded by `CHANGES_REQUESTED`; **the approval still describes the code** (head identical to `approvedSha`, or differing only by a base-sync merge or a `trivial`-class comment/doc/formatting edit — anything else is stale, and when in doubt it is stale); **no unresolved `pendingDecisions`**; every comment answered and every agreed thread resolved; CI fully green; `mergeable` clean; and **the base is landable** — never a parent task's branch whose PR is still open (that would inject unreviewed commits into the parent PR) and never a join branch (retire it to integration first), reported as `approved_awaiting_base`, which is a waiting *button*, not a frozen task. It posts the authorization record on the PR **before** merging (**NO SILENT MERGES**) and records `autoMerge` in the task file. Policy knob: `run.json.approvalMergePolicy = "auto"` (default) | `"off"`; the separate explicit user grant (`mergeAuthorization`) still applies to its named scope.
- **Draft ⇔ not reviewable, and readiness is the skill's own call.** A PR is draft only while an agent is in flight, the gate/CI is **not terminal-and-green on the PR's current head SHA**, the self-review hasn't run, the body is unwritten, or a **blocking open decision** is unanswered. **"CI has no failing check" is NOT the readiness test** — an empty or not-yet-created check set has no failing check either, and queued is not failing; that wording un-drafted two PRs onto code nothing had verified (one on "no CI checks report on this branch", one with two checks still `QUEUED`). The test is positive: checks reported on *this* SHA, non-empty, all terminal, none failed — otherwise stay draft with `draftReason: "ci_pending"` and let the next tick un-draft it. Only a repo *confirmed* to have no CI is exempt (`ciExpected: false`, with the reason). **Being stacked on an unmerged base is NOT a reason to stay draft** (that's what stranded whole cycles in draft) — stacking is stated in the PR body instead. The readiness checklist runs at PR-open and every monitor tick, and the agent un-drafts itself when it passes. **Never ask the user whether to mark PRs ready**, and never report a cycle as "ready for review" while any PR is a draft.
- **Open decisions must be actionable, never silent.** A choice that can't be settled on the merits (product/policy intent, ambiguous criteria, irreversible or security-relevant choices) is not a buried default: it becomes a numbered `D<n>` question posted on the PR with real options, the provisional default in effect, and an answer protocol; pinned at the top of the PR body; recorded in `tasks/<id>.json.pendingDecisions`; mirrored into `run.json.attention`; and (when `blocking`) it keeps the PR draft and disqualifies auto-merge until answered. Answers are harvested each monitor tick. If a human merges over an open decision anyway, it is carried into `run.json.unresolvedDecisions` and the final summary. Everything settleable stays autonomous — a decision-log line, not a question.
- **PR bodies are DURABLE, NOT VOLATILE — a description, not a dashboard.** A body is written once and read for days, so it must still be true next week. **Never state anything GitHub already renders live and the next commit can falsify:** file/line counts, test pass counts, coverage, timings, "CI green", mergeability, draft/review state, "N of M tasks merged". Write intent instead — what changed and why, **scope in words** ("touches `libs/storage/**` and its registration; nothing else"), the commands to verify (never their results), decisions + rollback, risks. **Events with their reasons are history, not status**, and belong ("#37 merged into the base and renamed the tables; the conflict was resolved keeping both intents"); so does a self-expiring condition ("built on #35; until it merges, its files appear in this diff too"). The test for every sentence: *would one more commit make this wrong?* → if yes it goes in a **comment**, where it reads as a timestamped event, not the body. Sole exception: the **⚠️ Open decisions** section, a live checklist by design. Current-state numbers live in `tasks/<id>.json` + the event log + the cycle report — never in prose a human will read a week later. (This rule already existed for the plan PR — "don't mirror status, GitHub renders it live" — and v3.5.0's `Files changed: N` violated it on task PRs; v3.10.0 generalizes it to every PR.)
- **Task ↔ PR identity is stamped everywhere a PR appears.** The human must never have to ask which PR is which task. Three surfaces, all mandatory — and **none is a label**: Cadence never creates a label and never labels a PR (the repo's label set belongs to its humans; a run passing through for days does not write to it). (1) an **identity header as the first line of every PR body, both sizes** — `**<T-id> · <what it does in plain words>** — cycle <slug> · plan PR #<n> · <tracker key> · base: <plain note>`; (2) the plan PR's **cycle map table** (`| Task | What it does | PR | Base |`), one write-once row appended as each PR opens; (3) in **everything Cadence writes** — a task id never appears without its PR number and a plain description, and a PR number never without what it does. Turn summaries render as a PR/Task/What-it-does/State table.
- **Evidence is captured as it happens, and the run ends with a cycle report.** Both levels append to their own **append-only** JSONL log (same single-writer rule as the state files): `events/run.jsonl` (orchestrator) and `events/<id>.jsonl` (each task agent), one line per event — spawns, complexity, PR opened/ready/re-drafted, decisions raised/answered, reviews and fix rounds, CI flips, base syncs, conflicts and how they were resolved, silent re-targets, scope checks, joins, blocked auto-merge guards, merges, stalls, escalations, failed gates, per-tick lines. A multi-day run cannot be reconstructed at the end, so an unlogged event is simply lost. **Two capture rules exist because both failed in production:** a `tick` line is appended on **every** wake-up, quiet ones included (a run that logged none could not say how often it woke or whether the backoff worked, so its entire cost section rendered `not captured`), and every anomaly gets an **`incident`** event as it happens — wrong briefs, topology skew, task collisions, external merges, Cadence's own errors — because one run's event log ended up *thinner* than its state files, with the orchestrator's three errors, a collision, an open risk and an answered decision existing only in `run.json`. **Cadence's own mistakes are the most valuable lines in the log.** **One event = one line, written whole:** a partial write followed by another puts two JSON objects on one physical line and **strict parsers abort there** — one such line made `jq` exit 5 and silently drop the **11 correctly-captured events after it**; a correction is a new line, never a patched one. **Never write a placeholder timestamp** (`00:00:00Z` is a lie the renderer computes durations from — omit the field instead). **An agent that stops early is an event** (`incident`, `agent.exhausted`), not a free-text note: context exhaustion is countable, and a run that recorded it only in `tick.note` had to report two further suspected instances as `not captured`. **And the two spawn ledgers must reconcile** — one run logged 16 `task.spawn` events against `tick.spawns` totalling 51, a threefold disagreement that made the cost section unrenderable; emit the event first and count the tick from the events actually written, and if they still disagree report **both numbers and the discrepancy** rather than the flattering one. Likewise **every** agent spawn logs `task.spawn`, ad-hoc repair/verification/housekeeping agents included, or the spawn census is fiction. **The kind vocabulary is CLOSED and the `kind` must match the `detail`** — the report looks events up by kind, so an invented kind isn't a richer log, it is a *lost* event that renders nowhere while the section it should have fed reads `not captured`. One run invented `cadence.defect`, `merge.executed`, `policy.skew` and `wave.dispatched` (all four already had canonical kinds) and mislabelled two more — a `pr.redraft` that was a body correction, a `gate.failed` whose detail said *"NOT a failure"*. If nothing fits, log an **`incident` with a new sub-`kind`**; never a new top-level kind. The orchestrator's own kinds are listed inline in `SKILL.md` (Evidence capture) because it had no reason to open the reference until render time, which is when it discovered the vocabulary it had spent the run ignoring. **Every `ts` — and every timestamped state field — comes from `date -u +%Y-%m-%dT%H:%M:%SZ`, never composed:** a whole run's timestamps were once local time suffixed `Z` (−3h off GitHub), internally consistent and absolutely wrong, which made every per-task duration unusable and left task files whose `readyAt` postdated their own `mergedAt`. GitHub's stamp wins where both exist, and at render time impossible orderings render `not captured` rather than being silently reconciled with an offset. From those logs, `<runDir>/report.md` is rendered at the end condition (and on demand via `/cadence:report`, marked `IN FLIGHT`): outcome, per-task table, **what needed the human** with wait times, **what went wrong — Cadence's own failures included**, flow health, cost, timeline, follow-ups, and a pasteable *Feedback for the maintainer* block. Two hard rules: **every claim anchors to a PR/comment URL/SHA/timestamp** (unlogged → `not captured`, never estimated), and **the failure sections are never softened** — an empty "what went wrong" on a run with re-drafts, stalls, or parked reviewers is a broken report. Format and event kinds: `references/cycle-report.md`.
- **Paths are announced, and notifications are rare and earned.** The run dir, plan doc, integration branch + plan PR, and `<runDir>/report.md` are printed in full **once at run open**, then carried as a **one-line footer on every turn** (`Run: … · report: … (/cadence:report to refresh)`) — including when the report doesn't exist yet, so the user knows it's available on demand. The report path is led with in the final summary and restated whenever the file is written. If a `PushNotification` tool is available, send **at most one per turn**, only on a *transition* worth interrupting a day for: the cycle finishing (with the report path), a **new** blocking open decision, the plan PR becoming ready for the human's merge, or a task marked `failed`. Track what was already pushed in `run.json.notified` so a pending item is never re-notified tick after tick, and **never notify for routine progress** (PR opened, CI green, review answered, base sync, quiet tick).
- **Every turn ends with an honest report.** Per-PR true state (draft *and why*, awaiting review, awaiting decision, approved, auto-merged, merged) plus the `attention` list — every open decision with its answer link, parked review loops, failed tasks, and the plan PR once ready.
- **One dedicated agent and one PR per task — no folding, ever.** Never combine two tasks into a shared branch/PR, and never fold a small task into a sibling's PR (a task agent may not touch another task's branch/PR, so it was never possible). Branch names are descriptive: `cadence/<slug>-t<id>-<task-slug>`.
- **Batching trivial work is a PLANNER decision — the prep bundle.** The planner may emit one task carrying several small **same-class** scopes (`docs` = no behavior change · `config` = config/scaffold/deps/CI · `schema` = migrations only, giving one revision chain), **never mixing classes** — mixing silently raises the PR to the riskiest item's level. Eligibility: small on inspection, no write-write conflicts among scopes or with other tasks, dependents content with bundle granularity (their edges re-point to the bundle), ≤5 scopes and ≤~15 files, and **every scope keeps its own R-ids** so the requirement ledger still balances (`0 unaccounted`). Bundles schedule early so they merge first and give the rest of the cycle a clean base. To the executor a bundle is just one task — one branch, one PR, one agent — with three adjustments: `complexity` = its **highest** scope's; a `schema` bundle **never** skips the pre-push self-review (min `/code-review low`); and the PR body carries **one labeled section per scope** (what/why/how-to-test/rollback) plus a line stating the scopes **revert as a set**. The scope check runs against the union touch set. A task agent that finds a scope doesn't belong reports it for re-planning instead of absorbing it. When in doubt: separate tasks.
- **Preflight PROBES the quality loop's capabilities, and a preflight fact is only true where it was measured.** Two capabilities are tested once and recorded with their fallback, never rediscovered per task: **(1)** whether anyone can actually be requested as a reviewer — GitHub *silently refuses to add a PR's own author*, so `gh pr edit --add-reviewer <self>` returns **exit 0** and leaves `reviewRequests: []`; when `ghLogin` is the PR author (Cadence's normal case) the review loop is **structurally inert**, which produced **seventeen PRs the run described as "awaiting review" when nothing could ever arrive**. Record `preflight.reviewers = "ok" | "self-only"`, and under `self-only` never call a PR *awaiting review* again — it awaits the human's **merge**, a different and honest sentence. **(2)** whether `/code-review` is invocable (it may carry `disable-model-invocation`) — one run had **thirteen tasks each rediscover this independently**. And because preflight runs in the **main checkout** while agents work in **fresh worktrees**, any fact resting on untracked or gitignored state records *where* it holds (`graphify = "main-checkout-only"`), never a bare `ok`: `graphify-out/` is gitignored, so every agent found no graph while the briefs kept promising graph queries.
- **Explicit dependencies at preflight.** The **superpowers plugin is a hard requirement** — the preflight gate STOPS the run with install instructions if its skills aren't available (per-task agents invoke `superpowers:*` throughout). **graphifyy is optional**: detected at preflight (`preflight.graphify = "ok" | "absent"`), used to ground analysis in graph queries when present, silently skipped when absent — it must never become a blocker.
- **Two-level, re-spawn-each-tick execution.** A *thin top orchestrator* (the main loop) only schedules/gates; it spawns one **per-task agent** per *idle active* task with work each tick. Agents are re-spawned every wakeup rather than kept alive, because monitoring spans days and an agent lives only one turn — continuity is the durable worktree + task file, not the process.
- **A detected merge is a DELTA, not a conclusion — the orchestrator never retires a task itself.** Seeing `mergedAt` appear starts the task's last step; it doesn't finish it. Cleanup (worktree, branch, join, tracker) and the final `tasks/<id>.json` write belong to the task's own agent, its sole writer — so a merge means **spawn exactly one monitor agent**, and record `done` only once it returns having written the file. Both halves failed in one production cycle, in both directions: four tasks were marked `done` on merge-detection with **no agent spawned at all** (worktrees left on disk, `handoff.delivered` never captured for their dependents, and one task file still reading `status: "open"` hours after its PR merged — found only because the user happened to ask about an unrelated task), while twice a cleanup agent was spawned **alongside the task's still-live agent** and both wrote the same file concurrently. Explicitly: never write a task file yourself, never spawn cleanup for a task with `agentInFlight = true`, never spawn cleanup alongside a monitor for the same task, and treat a merged PR whose file still reads `open`/`fixing` after its agent returned as an `incident` (`orchestrator.error`), not a tidy-up. **Idle-gating has no exception for cleanup.**
- **`agentInFlight` is a CLAIM, reconciled against reality every tick.** Idle-gating skips any task whose flag is set, so a task marked in-flight whose agent was **never spawned** is invisible forever — and that is not hypothetical: one production task was written to state as `implementing`/`agentInFlight: true` with the `Agent` call never issued, sat at its empty base branch through ~30 ticks, blocked two dependents, and cost **~6h of critical path** before anyone noticed it had outlasted every sibling. The same run failed in the **opposite** direction, spawning two spec agents it never recorded. So every tick, before deciding what to spawn, each in-flight task must show evidence an agent actually touched it — **branch head moved, task-file mtime advanced, or PR changed**. A full tick with none of the three → `incident` (`orchestrator.lost-dispatch`), reconcile status from git/PR (never from the flag), clear the flag, dispatch next tick. Evidence, not a stopwatch: a 30-minute lease neither spares a slow live agent nor catches a dead one quickly. **Write the flag from the spawn, never in anticipation of it** — set it after the `Agent` call is issued, in the same breath as `task.spawn`. And a lost dispatch belongs in `run.json.stalls`, not only in `incidents`: that six-hour freeze was logged twice as an incident and never once as a stall, so the ledger a human consults to see what held the run up omitted the run's biggest delay.
- **Idle-gating + change detection.** Only act on a task with `agentInFlight = false`. A task whose agent is mid-round-trip (`specifying`/`implementing`/`fixing`) is skipped; a settled `open` PR gets a monitor tick **only when the orchestrator's one batched read-only GraphQL snapshot (`run.json.prSnapshot`) shows a delta** — no delta, no spawn, with three narrow exceptions that are real work rather than polling: its readiness or auto-merge guards could now pass, its base advanced (base-sync / join refresh / join retirement), or an open decision is due its one reminder. Change detection is strictly read-only: the orchestrator never triages, replies, or acts on PR content.
- **Base moves are first-class signals, and conflicts are top priority.** When a human merges, the dependents' PR fields do not change — only their **base ref** does. So the change-detection call also snapshots the head OID of the integration branch and every task/join branch (`run.json.refSnapshot`), and **a moved ref is a delta for every PR based on it**, fanned out to all open dependents **in the same tick** (not one per wake-up). Two related rules: **`mergeable: UNKNOWN` is never "no news"** (GitHub computes it lazily; `UNKNOWN == UNKNOWN` must not read as quiet — stamp `unknownSince`, re-query, and after ~3 tries decide locally with a dry-run merge), and a PR that is `DIRTY`/`BEHIND`/`CONFLICTING` gets an agent **every tick until clean**, goes back to draft meanwhile (`draftReason: conflict`), and makes the run HOT (backoff resets).
- **Base syncs MERGE the base in — never rebase, never force-push an open PR.** Use `gh api .../pulls/<n>/update-branch -X PUT`, falling back to a local `git merge origin/<base>`. A force-push unanchors a human's in-flight inline comments and can dismiss their approval; a merge commit is the cheaper price. Squash-merged parents are the known trap: the parent's work lands on the base as one new commit while the child still carries the parent's original commits, GitHub silently re-targets the child when the parent's branch is deleted, and the same change now exists twice — resolve those hunks **in the base's favour** (the branch's copy is a stale duplicate). `headDelta: 'base-sync'` is an allowed, approval-preserving delta.
- **Scope check after every sync — the diff must be the task's own work.** `git diff origin/<baseBranch>...HEAD --name-only` must contain only paths this task legitimately touches (its brief's touch set + what the spec justified). Foreign paths mean the sync resolved wrongly: fix and re-check **before** offering the PR for review; record `filesChanged` + `scopeCheck` in the task file and echo `Files changed: N` in the PR body. A conflicted or scope-polluted PR is not `ready` (readiness checklist item 6) — an unexplained 40-file diff for a 3-file task is a defect, not a big task.
- **Adaptive monitor cadence.** The `ScheduleWakeup` interval is `monitorBackoff`-driven: base 180s while hot (deltas / spawns / agents in flight), doubling per fully-quiet tick to a `maxSeconds` cap (default 1800); any activity resets it. Never a fixed frenetic interval, and never an external scheduler.
- **Model-by-phase, with a fused fast path.** Spec/analysis is always **Opus, high effort**; implementation is Opus or Sonnet by the `complexity` the spec phase determined; monitor/fix/cleanup is **Sonnet, low**. Complexity is `high | medium | low | trivial`, decided during the spec phase, not at plan time. A spec agent that decides **`trivial` — and only `trivial`** — continues straight into implementation in the same invocation (one spawn, no context re-derivation); `low`/`medium`/`high` all stop at `specified` for a separately-tiered implement agent. **Fusing forfeits the tier**: one invocation is one model and spec is always Opus/high, so anything fused is *built* on Opus regardless of its complexity. When `low` fused too, the cheapest tasks ran on the most expensive model while `medium` ran on Sonnet — the cost curve inverted and cycles ran nearly all-Opus. `trivial` keeps the fast path only because there the spawn genuinely costs more than the model.
- **Spec consumes the planner's brief — verify-and-extend, never re-derive.** The plan's per-task context brief (touch set + requirements + acceptance criteria) is the spec phase's starting point; it is verified against current code (graphify-first when available) and extended on drift, with sub-subagents spawned only for genuine unknowns. Re-running full from-scratch analysis per task is the double-payment this rule exists to kill.
- **Complexity-gated pre-push self-review.** Before opening a task PR (after the green lint/format/tests gate), the implement agent runs a self `/code-review` scoped to *its own branch diff*, scaled to `complexity`: **`trivial` skips it** (a typo/lint/doc change with no behavior change — the gate is enough, don't make it bureaucratic); `low`/`medium` → `/code-review low`; `high` → `/code-review high`. This is a pre-PR self-review, separate from the JUDGE-BEFORE-YOU-ACT monitor loop that answers reviewer comments on an open PR.
- **Bounded review loops (REVIEW CONVERGENCE BOUND).** Both review loops have hard convergence bounds so a cycle can never stall in endless reviews: the pre-push self-review runs **exactly once** (one review, one fix pass — after fixes only the lint/format/tests gate is re-run, never a second `/code-review`); the monitor loop allows at most **3 fix→re-request rounds per reviewer** (tracked in `tasks/<id>.json.reviewerFixRounds`) — after that the agent stops re-requesting that reviewer, posts one summary comment, and parks the remaining findings for the human, letting the PR go quiet so the adaptive backoff engages. Per reviewer, not per PR: humans and other reviewers are unaffected. Neither cap ever blocks fixing genuinely broken code (red CI, conflicts, real bugs).
- **JUDGE BEFORE YOU ACT + NO SILENT FIXES.** Reviews are suggestions to evaluate on the merits (agree / alternative / decline / clarify), never commands. Every code change made in response to a comment/CI/conflict must get a real, *verified-posted* `gh` reply (capture the URL) before it counts as handled; agreed-and-fixed items also resolve their review thread and re-request the reviewer.
- **Sequencing: a dependent follows its blocker's DECISIONS, then its CODE.** A dependency edge exists because one task needs what another **decides and builds**, so running them concurrently doesn't make the second faster — it makes it *guess*. Two gates, each clearing on another **agent's** progress and never on a human's merge: a dependent's **spec** waits until every blocker is `specified`+ (its `handoff.contract` written — the decided interface, not a prediction); its **implement** waits until every blocker is `open`+ (PR open: code complete, gate green, self-reviewed). A `trivial` task may fuse spec→implement **only** when its blockers are already `open`. The flow audit classes these as `awaiting-blocker-spec` / `awaiting-blocker-pr` — legitimate sequence, distinct from `waiting-for-merge`, which stays a defect. Independent tasks still run fully parallel; the gate is per edge, not per wave. (v3.11.0 let a dependent's spec run as soon as its blocker's *branch* existed: it then planned against a tree without the blocker's work, and opened PRs built on an interface nobody had decided. The rule is "never wait for a **merge**", not "never wait".)
- **Knowledge transfers by written handoff — agents never share a context.** A task agent is spawned fresh, does one step, and dies; its dependents' agents have no memory of it, and the planner's brief is a *prediction* made before any code existed. So each task writes `handoff.contract` at the end of spec (exact surfaces it will produce — names, signatures, routes, entities, migrations — plus decisions and deviations from the brief) and `handoff.delivered` when its PR opens (what actually shipped, drift from its own contract, and the gotchas a consumer would otherwise rediscover). **The orchestrator pastes every blocker's handoff verbatim into a dependent's brief**, labelled, and **the handoff outranks the brief** where they disagree. A surface that is missing or differs at implement time is a `contract.mismatch` incident to surface, never something to stub around.
- **Every cycle ends with an EXIT GATE task, and the planner emits it by default.** Each task is verified against *its own base*; nothing verifies the **union** — the interaction of tasks built in parallel, and the suites that don't run per-PR (fresh-DB migration order, e2e/real legs). That is a structural hole in per-PR CI: a cycle once merged a migration that failed on any fresh database because the only suite that would have caught it runs on a manual workflow input. So the plan's last task depends on **every** other task, runs the repo's complete gate plus the cycle's own end-to-end promise through production code paths, owns the cycle-level acceptance criteria no single task owns, and touches **tests/harness only** — needing a production change is a finding to report, not to absorb. It is the one task allowed an empty R-id list. If the source plan already ends with an equivalent phase, adopt it; never emit two.
- **Branches are PUBLISHED AT SPEC START — this is what makes a cycle flow.** A task agent pushes its branch the moment its worktree exists, **empty, before writing a line of code**, and keeps pushing commits as it implements rather than saving them for PR-creation. A task's branch existing on the remote is what makes its dependents dispatchable, so publishing late is the same freeze as gating on merges, wearing the name `waiting-for-blocker-branch`. Pushing only at PR-creation meant a dependent waited out its blocker's build, gate, self-review **and** PR body — observed live: *"Merged (9): T1–T9 · Implementing: T10 · Pending (6): T11–T16 … the tail is serial by design."* It is not by design. An empty branch is inert (identical to its base, no PR, unreviewed) and costs a ref; publishing it means a dependent can cut its worktree the instant its **sequencing gate** clears, instead of waiting for a branch to appear. It does **not** license starting early — sequencing is governed by the two-level rule above. Never force-push: a dependent may already be based on what was pushed. `waiting-for-blocker-branch` on a blocker that has already been **dispatched** is a defect, not patience. **And the ORCHESTRATOR must accept an empty branch as a valid base** — "exists" means the ref is on the remote, not that it has commits, differs from its base, or has a PR. The rule was written only to the task agent, so the other half broke: an agent pushed an empty branch precisely to open the gate, the orchestrator judged that unsafe and held the dependent, and a `low`-complexity task's Opus spec was serialised behind its blocker's entire implement + gate + self-review + PR write-up. Refusing a dispatch because a branch "has nothing in it yet" is the same freeze under a different name; log an `incident` (`orchestrator.error`) on catching it. What governs *when* a dependent starts is the sequencing gate, never the emptiness of a ref.
- **A relayed GOTCHA meets the same evidence bar as a PR claim.** Harvesting a lesson from one agent and broadcasting it is one of the orchestrator's most valuable acts — and it multiplies a wrong one by the number of agents it reaches. Every relayed entry carries **the command that proved it, or a `file:line`**; no provenance, no broadcast. A gotcha was once relayed to *every remaining implement brief* claiming `--testPathPattern` is ignored by a jest project when the **positional path** is what that project ignores — and the failure mode is the dangerous kind: a run that quietly executes the whole project instead of one file **reads as a pass**. A sibling gotcha the same run had the same shape (`jest -t` takes a regex, so a plain-text `-t` matched nothing, ran **zero** tests, and reported all-skipped — also green). Hence two standing rules: **prefer a gotcha that names a command over one that states a conclusion**, and **an all-green result is not evidence a test ran** — check the suite/test counts and the tail line. A gotcha later found wrong is an `incident` (`orchestrator.false-gotcha`) **and** a correction pushed to every agent that received it.
- **Briefs state the RULE, never a derived number — or a STALE OBSERVATION.** The orchestrator may pass facts it can point at (paths, requirement ids, a blocker's PR number, the plan's own words) but never a count, total, or arithmetic claim it computed — it writes the rule and the agent, standing in the worktree, does the counting. Three wrong numbers reached briefs in one production cycle (a double-counted touch set; an unverified "this file is generated" relayed from another agent; and `REQUIRED_PATHS` "21 → 23", which confused OpenAPI *path keys* with *operations* — the real delta was zero, and an agent trusting it would have padded the array with paths that don't exist and shipped a false docblock). All three were caught only because the receiving agents counted for themselves. **The rule covers observations, not just numbers** — both fail identically: true when looked at, asserted as true when the agent acts hours later. The same cycle told a task the compose `db` container was running; true when measured, false when used. So never state the current condition of anything the orchestrator doesn't own and can't re-check for the agent: a service being up, a port being free, a branch's contents, a file existing, a check's result, "the tree is clean". Those are things the agent is standing next to and the orchestrator is not. A number **or observation** that must be passed on is labelled **unverified** with its source *and when it was observed*; an agent that finds a brief's claim false **declines and reports it** — correct behaviour, recorded as an `incident` (`kind: "brief.false-premise"`).
- **No agent ever waits inside a tick.** A monitor pass is one observation and at most one round of action: no `sleep`, no poll, no retry-until-green, no "check again in a moment". CI still running *is* the answer — return `prState: ci_pending` and let the orchestrator's adaptive backoff do the waiting, which is free. A monitor that looped on CI instead of returning burned ~80k subagent tokens per pass across four passes and had to be killed with `TaskStop`, having learned nothing the next tick wouldn't have learned for nothing.
- **A task agent writes its task file before it returns — always.** `tasks/<id>.json` is the sole durable record of a task and its agent is the sole writer; the orchestrator will not reconstruct it from GitHub. Returning without writing status + everything learned this invocation (PR, base, complexity, draft state + reason, decisions, approvals, scope check) leaves state lying for the rest of the run — in production a task file said "still specifying, nothing merged" while its PR had long since landed. **A step completed but not written down did not happen.**
- **One orchestrator per task.** Before spawning a `pending` task's first agent, check the remote: if the task's branch already exists, or a PR matching `prTitlePattern` for that task id is open, **do not spawn** — record `possible-concurrent-session` in `attention`, log an `incident` (`kind: "task.collision"`), and let the user decide who owns it. Adopting the branch, opening a second PR, or force-pushing over it are all wrong; the other session may be mid-write and neither can see the other's state. The one collision seen in production was caught purely by chance.
- **`main` is watched, and a moved `main` is a cycle-wide delta.** `refSnapshot` covers `main` as well as the integration and task/join branches. The repo doesn't stop while a cycle runs: an external merge can change the foundation everything is built on. When `main` moves, merge it into integration promptly (merge, never rebase — the plan PR is open), scope-check against both parents, and treat anything it breaks as a first-class finding in `attention` + an `incident` + the report. Waiting for the plan PR to turn red is finding out too late — that is how an external merge silently broke an already-merged migration and left a merged guard semantically dead.
- **Flush state before running out of room — the last writes are the ones that get lost.** The end of a run is when context is longest and the pending writes matter most, so they are the writes most likely never to happen. One run's orchestrator ran down at exactly that point and froze the state mid-truth: **six task files still read `status: "open"`/`mergedAt: null` for merged PRs**, `prSnapshot` still called the plan PR a draft, and `exitVerdict.caveat` still said *"no task PR has merged"* on a cycle where all sixteen had — so the report had to reconstruct six tasks from GitHub, which is precisely what state exists to prevent. Reconcile-and-flush is a **step**, not a hope: before the final summary, and on any tick where context is getting long, every merged PR must have a task file saying so (spawn its monitor agent — the orchestrator still never writes task files), `prSnapshot` re-baselined, `attention`/`stalls`/`exitVerdict` rebuilt, falsified caveats rewritten. **Render the report EARLY rather than perfectly** — one written while there is room beats a better one that never gets written.
- **Turn-end invariant.** If any task is still active or the plan PR isn't merged, the last action of the turn **must** be a `ScheduleWakeup` (at the current adaptive interval) re-entering `/cadence:ship <plan-path>`. Monitoring uses only in-session `ScheduleWakeup` — never cron or any external/paid scheduler.

## State model (per-run directory, split by owner)

Executor state lives under `.cadence/cycles/<YYYYMMDD-HHMM>-<6char-hash>-<slug>-cycle/` (add `.cadence/` to the target repo's `.gitignore`; never commit cycle state). Ownership is strict and is the reason state is a directory rather than one file — parallel agents would clobber a shared JSON:

- `run.json` — **orchestrator-owned** (only writer): roster, wave schedule, preflight gate (incl. `plugins.superpowers` / `graphify`), integration/plan-PR pointers, `prTitlePattern`, `modelPolicy`, `agentInFlight` flags, `prSnapshot` change-detection baselines, `monitorBackoff` adaptive-interval state, `approvalMergePolicy`, `attention` (the rebuilt-every-tick "needs you" list), `stalls`, `unresolvedDecisions`.
- `tasks/<id>.json` — **task-agent-owned** (each task's agent is the sole writer): that task's status, branch + `baseBranch`/`joinBranch`, worktree, PR number, `isDraft`/`draftReason`/`readyAt`, `pendingDecisions`, `approvals` (per-reviewer, with the `approvedSha` the auto-merge staleness test anchors on), `autoMerge`, `answeredComments` (with `replyUrl` proof), and `decisionLog`.

Task status flow: `pending → specifying → specified → implementing → open → (fixing ↔ open) → merged → done` (or `failed`); the fused fast path for **`trivial`** complexity goes `specifying → open` directly (the spec agent implements in the same invocation). `open` spans draft and ready — the draft flag is re-evaluated by the readiness checklist every tick, never by asking the user. Full schema and field notes: `plugins/cadence/skills/cadence-executor/references/execution-state.md`.

## Evolving a plugin from a cycle report (the feedback loop — INTERACTIVE)

This repo is where Cadence gets better, and the input is **evidence from a real run**:
the user finishes a cycle, takes its report (`<runDir>/report.md`, or the *Feedback for
the Cadence maintainer* block from it), and brings it here. **Whenever a cycle report —
a file, a path, or pasted text — arrives in this repo, run this loop. It is not a
silent, one-shot edit: it is an interactive session with the user.**

1. **Ingest and anchor.** Accept a report file, a run dir, or pasted text. Read it whole
   before proposing anything. Work only from the report's evidence (PR numbers, comment
   URLs, SHAs, timestamps, event counts). If the user adds a complaint with no evidence
   in the report, keep it — but label it `unverified` and say what evidence would settle
   it next cycle.
2. **Extract findings, don't editorialize.** One finding per symptom:
   `symptom → evidence → the rule/file in the plugin that produced it → class`.
   Classes: **behavior defect** (a rule did the wrong thing), **missing capability**
   (no rule covered it), **doc gap** (behavior was right, the docs misled), or
   **not-the-plugin** (repo/CI/process issue — say so plainly instead of adding a rule).
   Findings that trace to the same rule get merged into one.
3. **Triage WITH the user — `AskUserQuestion` is mandatory here, not optional.** Never
   guess what to fix or how ambitious to be. Ask in batched rounds (≤4 questions per
   call, options with a recommendation first):
   - *which findings to address this round* (multi-select — a report usually carries
     more than one round's worth);
   - *for any finding with more than one reasonable fix*, which approach, with the
     trade-off spelled out in each option;
   - *explicit confirmation for anything that touches an executor invariant* (merge
     policy, draft semantics, `main` safety, the planner↔executor contract) — those
     changes are never inferred from a report alone;
   - *scope* when a fix could be a small guard or a new subsystem.
   Do **not** ask what the report already answers, and don't re-ask something the user
   settled earlier in the session.
4. **Propose before editing.** For each accepted finding, state the exact file and rule
   you'll change, what the new behavior is, and the bump class it implies. Let the user
   correct the plan while it's cheap.
5. **Apply.** Edit the skill/reference files (behavior first, docs second), keep
   `SKILL.md` and its `references/*.md` in sync, and update this file's invariant list if
   an invariant actually changed.
6. **Version, tag, and record.** Bump per the versioning policy below and tag the commit.
   Write the round to **`docs/feedback/<YYYYMMDD>-<slug>.md`**: the findings, what was
   changed for each, and — importantly — **what was deliberately NOT changed and why**.
   That file is what makes the next cycle's report comparable to this one.
7. **Close the loop out loud.** Tell the user, per finding: fixed (and where), declined
   (and why), or deferred (and what evidence would change the call). If a finding needs
   another cycle to confirm, say which report field will show it.

**Honesty rules for this loop.** A report is evidence, not a verdict — judge each finding
on the merits (a reported "bug" is sometimes correct behavior, and saying so with the
reasoning is more useful than a reflexive rule). Never add a rule that only papers over a
symptom, and never quietly widen scope beyond what the user picked in step 3.

## Versioning policy (bump on every AI enhancement)

**A version marks a batch that is handed over, not an edit.** One version per *shipped batch* — never one per edit, per follow-up, or per turn in the same working conversation. A session that fixes six things is **one** bump sized by the largest change in it, not six bumps. (Minting a version per edit is how `3.3.0` became `3.10.0` in a single afternoon with nothing validated in between; each number then means nothing and the tag list stops being useful.)

**How it works in practice:**
- **While working:** accumulate entries under `## Unreleased` in `CHANGELOG.md`. Commit freely — commits are cheap and reversible, versions are not. **Do not touch `plugin.json` or create a tag.**
- **When the batch is handed over** — the user says ship/release, or the session's work is done and reported — bump `plugins/cadence/.claude-plugin/plugin.json` **once**, move `Unreleased` into a version heading, commit, and tag.
- **If unsure whether the batch is finished, don't bump.** An unversioned improvement sitting in `Unreleased` costs nothing; a released version you immediately supersede costs the meaning of every other number.
- **A version nobody has run is a candidate, not a result.** Prefer letting a batch be exercised by a real cycle (and its report) before stacking another release on top of it.

The bump size follows the largest change in the batch (`MAJOR.MINOR.PATCH`):

- **PATCH** (`x.y.Z`) — wording clarifications, typo/formatting fixes, tightening prose, or reference/template edits that do **not** change any skill's behavior or the planner↔executor contract.
- **MINOR** (`x.Y.0`) — backward-compatible additions: a new skill or command, a new optional plan-doc/state field, or added behavior that doesn't break existing plans or state files.
- **MAJOR** (`X.0.0`) — breaking changes: renaming/removing a skill or command, or any change to the plan-doc metadata header, filename convention, wave/touch-set fields, or state schema that would break plans or `.cadence/` runs produced by an earlier version.

When a batch spans several types, bump by the highest that applies. State the resulting version in the change summary, and record the release and its reasons in `CHANGELOG.md`.

**Every version bump MUST also create a git tag** (one tag per release, so the tag list reads as a release history rather than an edit log) on the commit that contains the bump, and the tag MUST be pushed together with the commit. Tags are plugin-scoped (the marketplace can host several plugins, each with its own version): `<plugin>-v<MAJOR.MINOR.PATCH>`, e.g. `cadence-v3.2.0`. Use an annotated tag whose message is a one-line summary of the change (`git tag -a cadence-v3.2.0 -m "…"`), then `git push origin <tag>` (or push with `--follow-tags`). A bump without its tag is incomplete — if you find a bumped version with no matching tag, backfill the tag on the commit that introduced that version.

## Documentation per plugin (philosophy)

**Every plugin ships its own deep-dive doc at `plugins/<name>/README.md`** — the comprehensive, human-facing reference for that plugin (concepts, worked examples, diagrams, command reference, state model, FAQ). The repo-root `README.md` stays a thin marketplace index that points into each plugin's doc. The per-plugin README is *documentation only*: the `SKILL.md`/reference files remain the source of truth for behavior, so keep the doc in sync when behavior changes — but editing the doc alone does **not** require a version bump (it changes no skill behavior or contract). Cadence's is `plugins/cadence/README.md`.

## Conventions when editing skills

- **Keep commands thin, behavior in skills.** A `commands/*.md` file resolves arguments and loads a skill; don't duplicate skill logic into it.
- **Templates are references, not prose.** PR body shape lives in `references/pr-template.md`; plan-doc shape in `cadence-planner/references/cycle-plan-template.md`; state schema in `references/execution-state.md`. Edit the reference, and keep the SKILL's inline summary in sync with it.
- **The planner/executor contract is load-bearing.** If you change the plan-doc metadata header, filename convention, or wave/touch-set fields, update *both* skills — the executor parses what the planner emits.
- Preserve the frontmatter `name`/`description` in every `SKILL.md`; the `description` is what triggers the skill and is intentionally verbose.
